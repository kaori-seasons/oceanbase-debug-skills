# CPU 与 IO 归因：处置边界

## CPU 密集

确认：主机用户态 CPU 高，业务执行耗时和运行队列同时上升。

动作方向：按租户和 SQL_ID 找消耗来源；load average 不能单独作为 CPU 饱和证据。

验证：复采原对象，确认对应异常持续下降且业务恢复；如果只改善一个指标而错误率仍高，继续检查 [query](../../oceanbase-query/SKILL.md)。

## IO 等待

确认：设备延迟/队列升高且 SQL IO 等待或合并积压同步。

动作方向：映射设备到数据/日志挂载点，区分读、写与回收。

验证：复采原对象，确认对应异常持续下降且业务恢复；如果只改善一个指标而错误率仍高，继续检查 [compaction](../../oceanbase-compaction/SKILL.md)。

## 后台争用

确认：资源峰值与合并/迁移时间线重合。

动作方向：协调后台任务与业务容量，单设备 util 高不足以决定限流。

验证：复采原对象，确认对应异常持续下降且业务恢复；如果只改善一个指标而错误率仍高，继续检查 [balance](../../oceanbase-balance/SKILL.md)。

L0 为有界只读查询与日志检查；L1 为有副作用的会话诊断；L2 包括改参数、终止会话、重启及侵入式采样；L3 包括强制副本/事务操作、故障注入和直接删除存储文件。debug_sync 不作为常规生产诊断。

任何变更必须记录原状态、目标范围、停止条件和恢复方案。终止事务与重启没有等价逆操作，不能把“重连”写成回滚；应说明重试、事务一致性及业务补偿。不得为了临时恢复随意关闭写限流或扩大内存上限。
